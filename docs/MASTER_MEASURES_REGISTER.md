## 0. How to read this register

- **Source Classification**
  - `DIRECT` — the exact value (or a straight percentage/average of a single always-present field) returned by an upstream API/DB column, no business logic applied beyond unit conversion/rounding.
  - `DERIVED` — computed client- or server-side from one or more DIRECT fields via a documented formula in this codebase.
  - `AGGREGATED` — a count/sum/average over a population of DIRECT/DERIVED rows (e.g. "total calls", "FCR rate").
  - `CONFIGURED` — a value set in this app's own configuration/schema (theme tokens, role permissions, campaign config), not business telemetry.
  - `MOCK` — fabricated/placeholder data with no live backend behind it at all.
  - `UNKNOWN` — lineage could not be confirmed in the time available for this pass; flagged rather than guessed.
- **Verification Status**: `SOURCE VERIFIED` (traced to the real API/table field), `FORMULA VERIFIED` (the exact calculation code was read), `VALUE NOT YET VERIFIED` (lineage traced but no live value was checked against ground truth — out of scope this session per the brief).
- Route coverage is the authoritative list from `src/App.tsx` (31 routes, read in full this session), not the suggested list in the brief — a few extra routes (`/customers`, `/customers/:id`, `/chat`, `/ratios`, `/ratios/:id`, `/role-management`) exist and are covered; the brief's own list names were matched to these.

## 2. Core shared data sources (read once, reused by many screens)

### 2.1 `GET /api/calls/data` → `CallDataResponseDto` (`src/types/api/calls.ts:88-101` for summary shape)
The single upstream "call-data" feed. Two genuinely different code paths produce the `summary` object depending on the caller's Business Data Scope (`api/calls/data.ts:60-98`):

- **Unscoped caller** (`access.allCategories` true, or `authorizedAgentIds === 'all'`): the `summary` object is the **upstream Voice API's own aggregate, passed through verbatim** — `fcr_rate`, `escalation_rate`, `avg_aht_seconds`, `avg_intent_accuracy`, `total_calls`, `resolved_count`, `escalated_count`, `active_calls`, `connecting_calls`, `transfers_today` are whatever that external system computed, with an **unknown internal formula/population/date-range** from this app's point of view. Classification: `DIRECT` but the upstream formula itself is `UNKNOWN`.
- **Scoped caller** (Agent/Category Scope restricts the caller to a subset): `api/calls/data.ts:81-93` **recomputes** `fcr_rate`, `escalation_rate`, `avg_aht_seconds`, `avg_intent_accuracy`, `total_calls`, `resolved_count`, `escalated_count` **locally over only the authorized rows on the current response page**, flags the object `scoped: true`. Classification: `AGGREGATED`, formula verified, but the eligible population is explicitly **page-scoped, not a true global total** — the code's own comment (`api/calls/data.ts:25-29`) says exactly this.
- Formula used in the scoped path: `fcr_rate = (count where fcr===true) / totalCalls × 100`; `escalation_rate = escalatedCount / totalCalls × 100` where `escalatedCount` counts **every** row with `outcome==='escalated'` (not filtered to only resolved+escalated "handled" calls); `avg_aht_seconds = round(mean(duration_seconds))` over **all** rows with no stale-duration exclusion; `avg_intent_accuracy = mean(intent_accuracy)` over all rows.

This same feed, called with `status=active` and polled every 4s, is **Live View**'s data source (`useLiveCallData`), and called with `page_size=5` is one of **Dashboard**'s two Recent-Interactions sources.

### 2.2 `src/server/analytics/ratioRegistry.ts` + `src/server/analytics/ratioMath.ts` — the Ratio Explorer / Analytics / Dashboard Performance Ratios engine
31 named business ratios are registered (`BACKEND_RATIO_REGISTRY`). Of those, **exactly 6 are actually implemented** (`availability: 'direct'`); the other 25 are `backend_gap` / `partial` / `awaiting_telemetry` and display their `unavailableReason` text instead of a fabricated value, never 0% or a guess. This is the single most important fact for the whole register: **most of this app's "ratio catalogue" is a documented gap list, not live telemetry.**

Implemented ratios and their exact formula (`src/server/analytics/ratioMath.ts:96-154`), computed over the **complete** qualifying call-data population for the selected window (fetched via `callPopulationFetcher.ts` looping `status=inactive` pages — NOT the single-page `/analytics/metrics` aggregate, and NOT the same population/denominator logic as §2.1's scoped-summary path above):

| Ratio ID | Numerator | Denominator | Null rule |
|---|---|---|---|
| `fcr` | `fcr === true` count | **every** fetched call | 0 denom → null |
| `escalation_rate` | `outcome === 'escalated'` count | **"handled" calls only** (`outcome` is `'resolved'` or `'escalated'` — an indeterminate-outcome call is excluded from the denominator entirely) | 0 denom → null |
| `resolution_rate` | `outcome === 'resolved'` count | same "handled" population as `escalation_rate` | 0 denom → null |
| `aht` | sum of `duration_seconds` | count of calls with a finite, **non-stale** duration (`isStaleDuration()`, `src/lib/format.ts` — a ~4h+ guard) | 0 denom → null |
| `successful_resolution_time` | sum of `duration_seconds` for resolved calls | count of resolved calls with a non-stale duration | 0 denom → null |
| `authentication_success_rate` | `was_authenticated === true` count | calls where `was_authenticated` is **non-null** (an auth flow was genuinely attempted; `null` is excluded, never counted as a failure) | 0 denom → null |

→ **Confirmed cross-screen inconsistency #1**: "Escalation Rate" and "FCR" and "AHT" each have **two independently-coded formulas** in this codebase — the Ratio Explorer/Analytics/Dashboard-Performance-Ratios engine above (handled-population denominator for escalation/resolution, stale-duration-excluded AHT) vs. the Call Logs/Live View scoped-summary path in §2.1 (whole-population denominator for escalation, no stale-duration exclusion for AHT). Same labels, different numbers, by design of two separately-built features — not a bug introduced by any single change, but a real, user-visible discrepancy if the same viewer compares the Call Logs header strip to the Dashboard Performance Ratios strip or Ratio Explorer for the same time window.

→ **Confirmed cross-screen inconsistency #2**: `src/services/agents/agentPerformanceAggregator.ts:80-96` (AI Agents / Agent Detail's per-agent metrics) is a **third, independent** FCR/AHT implementation: FCR denominator = calls where `fcr` is **not null/undefined** (`fcrKnown`), explicitly handling a "no FCR value" case that `ratioRegistry.ts`'s own documentation (line 71) asserts cannot happen ("fcr is a required, always-present boolean... there is no 'not evaluated' state"). AHT here again excludes stale durations (agreeing with the ratio engine, disagreeing with §2.1's scoped-summary path). Whether `fcr` can genuinely be absent is therefore an open, unresolved question inside this very codebase — two of its own measure implementations disagree about it.

Dashboard's "Performance Ratios" strip (`DASHBOARD_PERFORMANCE_RATIO_IDS`, `src/lib/dashboardNavigation.ts`) and "Avg handle time" Live Operations tile both call `useRatioSummary` → this exact engine, so Dashboard agrees with Ratio Explorer (same source), but **not** with Call Logs' own header strip (§2.1).

### 2.3 QA ratio engine — `src/lib/qaRatios.ts` (`computeQaRatios`) + `src/lib/automatedQaRatios.ts` (`computeAutomatedQaRatios`, a thin field-rename adapter)
Shared by **both** Automated QA (`AutomatedQaInlinePanel`, `AutomatedQaInspector`, evaluation-scoped) and Human QA (`QaReviewDialog` summary panel, `QaQualityExplorer` presumably) for the 9 named QA parameters: `context_continuity_rate`, `followup_understanding_rate`, `reference_resolution_accuracy`, `task_progression_rate`, `unnecessary_clarification_rate`, `repetition_loop_rate`, `customer_correction_rate`, `conversation_recovery_rate`, `response_grounding_rate`. One real engine, two adapters feeding it (`findings`/`observations` from two different persistence models) — this is the one place in the app where the same measure genuinely IS computed identically everywhere it appears, by deliberate design (`qaRatios.ts`'s own header comment).

Denominator rules per parameter family (`src/lib/qaRatios.ts:29-70`):
- `response_grounding_rate`: denominator excludes `CANNOT_VERIFY` explicitly (only `GROUNDED`/`NOT_GROUNDED` are eligible).
- Interaction-level parameters (`repetition_loop_rate`, `customer_correction_rate`): rolled up **once per review**, not per turn — a review counts if it contains *any* qualifying turn.
- All other (turn-level) parameters: denominator excludes `N_A`; numerator is the clean value for "higher is better" parameters, the problem value for "lower is better" parameters.
- Every rate is `null` (never fabricated 0%/100%) when its denominator is 0.

### 2.4 `src/services/agents/agentPerformanceAggregator.ts` — AI Agents / Agent Detail roll-up
Pure client-side aggregation over already-fetched Interaction/ChatSessionSummary/CampaignWithStats rows, grouped by `agentId`. Explicit in its own header comment: `GET /api/v1/analytics/metrics` has **no per-agent breakdown** beyond a raw `calls_by_agent` count, so every per-agent number on AI Agents/Agent Detail is derived in the browser from the same rows Call Logs/Chat Logs already fetched — not a dedicated backend aggregate. Classification: `AGGREGATED`, formula verified; eligible population is whatever page of interactions happened to be loaded for that agent (same "page-scoped, not a confirmed global total" caveat as §2.1).
