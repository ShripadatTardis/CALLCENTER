## 1. What this session implements

The governance/metadata layer from `docs/CMA_SCHEMA_PROPOSAL_v0_3_1.sql` Parts 2/2A/3 — the tables
that record *what* a measure is, not how to calculate it:

- `cma_base_facts` — the governed, measurement-neutral vocabulary of atomic fields.
- `cma_dimensions` — governed filtering/grouping/attribution concepts (time, channel, agent,
  campaign, interaction source, outcome, customer).
- `cma_canonical_measures` — the unique business concept (e.g. "First Contact Resolution"), its
  governance status, and (when one exists) a pointer to the implementation treated as the
  resolved/migration reference.
- `cma_measures` — individual implementation/display occurrences of a canonical measure (e.g.
  `FCR-03`), each with its own formula/population/null-handling metadata and operational status.
- `cma_measure_dimensions` / `cma_measure_base_facts` — the many-to-many relationship tables.
- `cma_chart_visualizations` — the lighter-weight chart-to-measure/fact presentation relationship
  (§5.2 of the data model doc; charts never get a full canonical-measure row).

Plus a minimal read-only registry service/API (brief §7) and a deterministic seed built directly
from the real, current `docs/MASTER_MEASURES_REGISTER.csv` (brief §3) — not the prior session's
51/75/12 estimate, which the brief explicitly told this session to re-verify rather than treat as
an immutable target (brief §3: "Verify these counts from the actual register rather than treating
them as immutable targets").

CMA-1A/1B (`customer_interactions`, `call_center_sync_interaction`, the manual Sync Now UI) are
completely untouched by this session. No calculation engine, `evaluateCmaMeasure` pipeline, or
write-capable registry API was built — that is CMA-3's scope (brief §11).

## 3. How the registry was populated — methodology, not hand-typed rows

87 rows exist in the current `docs/MASTER_MEASURES_REGISTER.csv` (confirmed by direct count, not
assumed from any prior document). Given that scale, the seed is generated by
`.tooling/scripts/cma-registry-build.mjs`, a pure function of the CSV's content, rather than
hand-transcribed — this is what makes the seed genuinely "deterministic and repeatable" (brief §3):
re-running the generator against an unchanged CSV produces byte-identical SQL, verified directly
(two consecutive generations diffed identical).

**Grouping rule.** Rows are grouped into one canonical measure by their `Measure Name` column with
any trailing parenthetical qualifier stripped — e.g. "First Contact Resolution (unscoped)",
"(scoped recompute)", "(Ratio Explorer/Dashboard)", and "(per-agent)" all collapse to one canonical
measure, "First Contact Resolution", exactly the pattern the register's own §7.5 reconciliation
table uses for FCR/Escalation Rate/AHT/Intent Accuracy/Technical Performance. An ID-prefix heuristic
was deliberately **not** used — it would have wrongly merged all 25 distinct `RATIO-GAP-*` ratios
(each a genuinely different business concept) into one group.

**Two documented exceptions, applied explicitly, not silently:**
- A `QA-*` (live, per-review engine) row and a `RATIO-GAP-*` (population-level, unimplemented) row
  can coincidentally share the same stripped Measure Name (9 such pairs exist). The register's own
  text (`MASTER_MEASURES_REGISTER.md` §7.6) says these are "conceptually parallel but operationally
  separate... never mistaken for the same thing" — so the builder keeps each such pair as **two**
  distinct canonical measures rather than merging them, with the `RATIO-GAP` side's canonical name
  suffixed `(Population Ratio)` for clarity.
- `CAMP-02`/`CAMP-03` ("raw classification" vs. "policy classification") are, per §7.2, "two
  independently-maintained success definitions for the same target... not interchangeable" — a
  genuine difference in business definition, not a display variant of one disputed definition. The
  builder detects any `"... classification)"` qualifier pair and keeps them as separate canonical
  measures instead of folding them into one `pending_decision` group.

**Governance status derivation** (per canonical-measure group):
- `mock` (+ `measure_class = 'mock_indicator'`) when every occurrence in the group is a disclosed
  fabricated indicator (`Source Classification` containing `MOCK`).
- `unimplemented` when every occurrence in the group has no live implementation (`Original Data
  Source`/`Verification Status` saying "not implemented" — i.e. every `RATIO-GAP-*` row).
- `pending_decision` when the group has ≥2 live occurrences with genuinely distinct
  `Code File and Function` implementations — a real, currently-unresolved disagreement.
- `decided` otherwise — a single live implementation, or multiple display occurrences of the
  identical formula (e.g. `FCR-06`/`AHT-06`, documented in the register as reusing `FCR-04`/`AHT-04`
  unchanged).

**Occurrence classification** (brief §3's 4 required buckets, computed per CSV row, never omitted):
`mapped_to_canonical_measure`, `visualization_only` (chart rows), `pending_business_definition_decision`
(any occurrence under a `pending_decision` canonical measure), `not_yet_implemented_or_mock`.

**Base Facts and Dimensions are a fixed, hand-verified catalog**, not derived from free CSV text —
per brief §6 ("Maintain measurement-neutral Base Facts... do not introduce precomputed
numerator/denominator contributions... into the interaction storage"), these mirror real columns
already in `call_center.customer_interactions` (CMA-1A) plus the real `qa_findings`/
`automated_qa_observations`/`campaign_executions`/`campaign_results`/`campaign_classifications`
tables and the Call Metrics API's per-call latency field — nothing invented. Each measure
occurrence's base-fact/dimension relationships (brief §6) ARE derived from the CSV's own
`Numerator`/`Denominator`/`Exact Backend Field`/`Agent Scope`/`Channel Scope`/`Campaign Scope`/
`Date/Time Basis` columns — a measure only gets a dimension/fact relationship when the register
itself documents that scope for that row.

**Chart targets** (brief §5.2's exactly-one-target rule) are resolved by matching each chart row's
description against the already-built canonical measure names, or to one of 4 raw-count/latency
Base Facts when no canonical measure applies. One chart could not be resolved to a single fixed
target — flagged, not force-fit (see §5 below), independently reproducing the exact same gap
`CMA_DATA_MODEL_v0_3_1.md` §5.2 found by hand for the original, smaller proposal — a strong
cross-check that the automated resolution logic is sound.

## 5. Known, disclosed gaps (not resolved by this session)

- **`CHART-RT-01` (Ratio Trend) has no row in `cma_chart_visualizations`.** Its target is whichever
  canonical ratio the viewer currently has selected at view time — a dynamically-parameterized
  target, not the fixed, single target every other chart has. The table's `exactly_one_target`
  constraint, as designed, genuinely cannot represent this — the same limitation
  `CMA_DATA_MODEL_v0_3_1.md` §5.2/§7 already flagged for the original proposal. This session's
  automated chart-resolution logic independently found the exact same gap for the same chart,
  without being told about it in advance — a real cross-validation of both the design doc's
  original finding and this session's resolution logic, not just a repeated assumption. Needs
  either a nullable-target allowance or a genuinely different "parameterized chart" concept — not
  decided here.
- **9 `pending_decision`-adjacent business rules remain genuinely unresolved**: First Contact
  Resolution, Escalation Rate, Average Handle Time, and Call Technical Performance each have ≥2
  independently-coded live implementations with no recorded decision about which is authoritative.
  No screen's existing calculation was treated as authoritative by this registry (brief §4) —
  every occurrence under these 4 canonical measures is explicitly classified
  `pending_business_definition_decision`, never `mapped_to_canonical_measure`.
- **25 ratios remain genuinely unimplemented** (`RATIO-GAP-01`..`25`) — registered with a real
  business definition (carried from the CSV) but no live algorithm, correctly distinct from the 3
  disclosed mocks.
- **Dimension/fact relationships are only as complete as the CSV's own scope columns.** Where the
  register itself documented a scope as `unknown`/`N/A` for a row (common for the fully-unimplemented
  `RATIO-GAP-*` rows, which have no real formula to derive scope from), no relationship was invented
  for it — an empty relationship set for an unimplemented measure is the honest state, not a gap in
  this session's derivation.
- **Business Data Scope is not applied anywhere in this registry** — by design (brief §8: "Do not
  confuse a measure's supported dimensions with a user's authorization to access data within those
  dimensions... Actual evaluation must later apply the user's authorized Business Data Scope before
  aggregation"). This registry only records which dimensions a measure *could* be filtered/grouped
  by; CMA-3's evaluation pipeline is responsible for intersecting that with the caller's real scope.

## 8. Readiness for production migration

**Technically ready; not recommended to activate yet, by design.** §9's database validation
confirms the migration and seed are mechanically safe to apply (clean replay against the full real
migration history, clean idempotent re-application, correct authorization, zero relationship
defects) — there is no outstanding technical blocker. The reason to hold off is product, not
technical:
1. 4 `pending_decision` business definitions (FCR, Escalation Rate, AHT, Technical Performance) are
   real, standing product decisions this registry surfaces but does not make. Applying the registry
   to production before those decisions are made is harmless (the registry only records the
   disagreement, it does not pick a side), but CMA-3's evaluation pipeline should not be built
   against these four until a decision is recorded.
2. `CHART-RT-01`'s dynamic-target gap needs a design decision (nullable target vs. a parameterized-
   chart concept) before that one chart can be registered at all.
3. No downstream code depends on these tables yet (by design — CMA-3 is out of scope this session),
   so there is no urgency pressure to apply early; applying once CMA-3's actual consumption pattern
   is known reduces the risk of a schema change immediately after going live.

When the coordinator is ready: apply `20261027000000_cma_governance_registry.sql`, then apply
`supabase/seed/cma_governance_registry_seed.sql` (both are idempotent — safe to re-run), then
