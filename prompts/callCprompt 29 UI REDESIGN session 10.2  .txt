
SESSION 10.2 — VOICEFORCE FULL PRODUCT UX TRANSFORMATION

You are working in the existing Call Centre / VoiceForce repository.

This is a FULL-PRODUCT UX TRANSFORMATION session.

Session 10.1 established the production UX foundation:
- 52px compact icon rail
- temporary overlay navigation
- compact context bar
- Direction A-style dense operational tables
- refined Direction C dark navy visual language
- Direction C master/detail Create Campaign workflow
- accessibility/readability improvements
- production deployment

However, Session 10.1 intentionally transformed only the shell and selected campaign surfaces.

The rest of VoiceForce still contains substantial portions of the old UI inside the new shell:
- oversized cards
- large filter sections
- excessive whitespace
- tall page headers
- controls occupying too much viewport
- vertically stacked information that could be presented much more efficiently
- large bordered containers around sparse content
- detail pages that still look like the previous application
- inconsistent density and hierarchy between modules

The user has now explicitly requested a thorough redesign of EVERY VoiceForce page.

This is NOT a superficial theme migration.

============================================================
1. PRIMARY PRODUCT PRINCIPLE
============================================================

WORKSPACE FIRST.

The information or task the operator came to work with must dominate the viewport.

Navigation, filters, headings, controls, chrome and secondary information should consume as little persistent screen area as practical.

Target:

- approximately 90%+ of useful viewport available to working content where practical
- persistent application chrome approximately <=10%
- navigation remains compact and temporary/overlay where appropriate
- avoid large permanent control panels
- avoid decorative whitespace
- avoid giant cards merely because the old UI used cards

IMPORTANT:

DO NOT interpret "preserve functionality" as "preserve the current layout."

Existing page structure, card structure, component structure and information placement are NOT design constraints.

You MAY substantially reorganize the presentation of a page if doing so improves usability.

Preserve:
- real functionality
- real data
- permissions
- API semantics
- domain semantics
- business rules

Do NOT preserve bad layouts simply to minimize the diff.

============================================================
3. ABSOLUTE FILTER DESIGN RULE
============================================================

FILTERS ARE CONTROLS, NOT CONTENT.

Current Call Logs and similar screens allow filters and surrounding controls to consume a large portion of the upper viewport.

This must change.

For filter-heavy operational pages, use a reusable compact filtering model.

Preferred pattern:

[ Search................................ ] [important selector] [Filters 3] [View] [Export]

Clicking Filters opens a TEMPORARY FLOATING FILTER SURFACE.

The filter surface:
- overlays the workspace
- does NOT permanently push/reflow the primary data area
- closes with Escape
- closes appropriately on outside click
- has accessible focus behavior
- may be a floating popover/panel on desktop
- may become a temporary drawer/bottom sheet on smaller screens

Typical desktop width:
approximately 320–380px where appropriate.

When filters are active and the panel is closed:
- show compact removable filter chips where useful
- show active-filter count on the Filters button
- ensure the operator can immediately tell that filtering is active

Example conceptual toolbar:

Search interactions...   [Status ▾]   [Filters 3]   [Grouped/Table]   [Export]

Active:
[EMI Reminder ×] [Escalated ×] [Last 7 days ×]

Do NOT blindly put every filter in the floating panel.

One or two extremely common/page-critical controls may remain directly visible.

Secondary/advanced filtering belongs in the temporary panel.

VERY IMPORTANT:
Preserve actual filtering semantics.

If an existing filter only filters the currently loaded page:
- it must continue to say that honestly
- do NOT make it look like global/server filtering

Do not invent backend filtering.

Build reusable primitives rather than independent filter implementations for every page.

Possible conceptual components:
- CompactFilterBar
- FilterPopover / FilterPanel
- ActiveFilterChips
- CompactSearch
- ViewToggle

Names are illustrative, not mandatory.

============================================================
4. VIEWPORT DENSITY TARGET
============================================================

On a normal desktop / 1080p-class viewport:

After the compact application context/header, primary working data should begin as high on the page as reasonably possible.

For operational screens, aim for roughly 50–90px of control/header overhead between the context bar and primary data where practical.

Do NOT create:

[Huge title]
[Large subtitle]
[Four giant KPI cards]
[Huge filter card]
[Separate filter controls]
[Then finally the data]

Instead consider:

compact title/context + metric strip + compact toolbar + primary workspace.

Metrics should use compact strips / inline summaries where suitable rather than large cards.

- floating advanced filters
- active-filter chips

CHAT LOGS

CUSTOMERS

Explore a more operational presentation such as:

Preserve the established product meaning:

Redesign as a genuine conversation workspace:
- compact session setup controls

- composer remains prominent and practical
- avoid huge empty bordered rectangles purely for decoration

AI AGENTS

16. STOP CONDITIONS
============================================================

STOP and report rather than guessing if:

- a redesign would require changing business semantics you cannot determine
- a page depends on apparently fabricated/mock data and making it look production-real would be misleading
- authorization behavior is unclear and a UI change might expose unauthorized data
- a backend/API change becomes necessary to preserve functionality
- Partner API behavior would need to be guessed
- a test would require placing a real call/message
- a destructive production action would be required for verification

A stop condition may apply to one page without preventing safe transformation of the rest of the product.
