## Architecture objective

Introduce a clean integration architecture between the screens and the live backend.

The intended direction is approximately:

Existing React screens
↓
UI hooks / view-model layer where useful
↓
typed API/service layer
↓
backend adapters / transport
↓
our Voice Agent / Call Centre APIs

The screen components should not directly depend on backend transport details.

Future modules should be able to use the same architecture without creating ad-hoc API calls inside pages.

Do not over-engineer this. Use the existing React/Vite/TypeScript application and its installed libraries where practical.

## Key planning principle

For every existing screen element that currently uses mock/simulated data:

* Try to map it to a real field or capability in the live system.
* If there is no clear live mapping, do not automatically remove it and do not invent a mapping.
* Treat it as a decision point and recommend one of:

  * extend/add a backend API field or endpoint,
  * derive it from existing live data,
  * change the UI representation,
  * remove the field/control/metric because it no longer has a meaningful live equivalent.

These decisions must be made case by case.

The required end-state is **no mock/simulated/demo data**, but both frontend details and backend API contracts may evolve where justified.
